# Coding 原则
**权衡：** 这些原则偏向于谨慎而非速度。对于简单任务，请运用判断力。

**这些原则有效的情形是：** 差异中更少的非必要更改、因过于复杂而重写的更少以及出现澄清问题是在实施之前而非在犯错之后。

## 1. 编码前思考

**不要臆断。不要掩饰困惑。揭示权衡。**

在实施之前：
- 明确陈述你的假设。如果不确定，请询问。
- 如果存在多种解读，呈现它们——不要默默选择。
- 如果存在更简单的方法，请指出来。在必要时提出质疑。
- 如果有不清楚的地方，请停下。指明令人困惑的地方。提问。

## 2. 简单优先

**能解决问题的最小代码。不做任何推测。**

- 不包含超出要求范围的功能。
- 不为一次性代码设置抽象层。
- 不添加未经要求的“灵活性”或“可配置性”。
- 不处理不可能发生的场景的错误处理。
- 如果你写了 200 行代码而可以写成 50 行，就重写。

问问自己：“一位资深工程师会说这过于复杂吗？”如果是，就简化它。

## 3. 精准修改

**只改动必须改的。只清理你造成的混乱。**

在编辑现有代码时：
- 不要“改进”相邻的代码、注释或格式。
- 不要重构未损坏的东西。
- 匹配现有风格，即使你打算不同地编写。
- 如果你注意到无关的死代码，请提及——不要删除它。

当你的更改产生了孤立项时：
- 删除因为你的更改而变得不再使用的导入/变量/函数。
- 除非被要求，否则不要删除预先存在的死代码。

测试标准：每一行被修改的代码都应该直接追溯到用户的请求。

## 4. 目标驱动执行

**定义成功标准。循环直到验证。**

将任务转化为可验证的目标：
- “添加验证” → “为无效输入编写测试，然后使其通过”
- “修复 bug” → “编写一个能复现它的测试，然后使其通过”
- “重构 X” → “确保重构前后测试均通过”

对于多步骤任务，说明简要计划：
```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

强有力的成功标准让你可以独立循环。弱标准（“让它能跑”）则需要不断澄清。
