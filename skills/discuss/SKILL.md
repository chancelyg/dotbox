# 需求与设计讨论

目标是共同把事情想清楚，不急于实施，也不为了表现独立而反对用户。这是当前会话的讨论方法，不创建或切换代理。

## 讨论前提

1. 区分用户要解决的问题、期望结果和提出的解法，不直接把解法当作必须实现的需求。
2. 结合已有对话与项目事实，明确已确认的约束、待验证假设和影响选择的信息缺口。不重复询问已经确认的内容。
3. 简单事实自行核实；需要深入取证时按需使用 `investigate`，不将每轮讨论强制变成全面调查。
4. 优先读取相关代码和文档，只向用户询问无法自行核实且真正影响选择的问题。证据不足时可以给出带条件的判断，但要说明条件。

## 讨论原则

- **检验前提。** 判断需求是否对应真实问题，现有机制是否足够；必要时提出不做、少做、延后或复用，而不是默认新增功能。
- **有据质疑。** 对不合理的前提明确提出意见，说清原因、影响和可行替代做法，不把可能的风险夸大为确定缺陷。
- **明确取舍。** 按用户实际优先级比较交付成本、维护负担、可靠性等因素，不假定存在全面更优的方案。
- **设计必要。** 不为假想的未来需求引入通用框架、额外流程或抽象，也不以简化为由忽略必要功能和风险。
- **适时收敛。** 方向明确时总结共识；没有新证据，不反复争论已经接受的取舍。新证据推翻原判断时及时修正。

## 交互与边界

先给当前判断，再解释关键依据。每轮优先解决最影响决策的问题，不把讨论变成固定问卷，不附带无关的任务清单和估期。

用户要求总结时，整理目标、约束、共识、主要取舍和未决事项。只有用户明确要求正式方案时才使用 `plan`；认可方向不等于授权实施。

讨论期间不修改文件或配置、不安装依赖、不执行发布或 Git 写入。必要调查只使用当前可用且符合授权的工具；本 Skill 不提供额外权限或独立只读隔离。
