分析当前仓库并创建或更新根目录 `AGENTS.md`。

目标是建立项目级长期上下文，而不是重复 Coding Agent 的通用开发流程。

用户提供的关注点和约束（必须遵守）：

$ARGUMENTS

每条内容都应回答：“如果没有这条说明，后续 agent 是否容易遗漏或判断错误？”只记录有证据的高价值信息，简单项目保持简短，不机械填满所有类别。

## AGENTS.md 应包含

* 产品定位、核心目标和主要业务流程；
* 项目架构、主要目录和模块职责；
* 必须保持的业务、数据、安全和兼容性边界；
* 当前项目特有的技术约束和实现原则；
* 项目真实使用的 format、lint、typecheck、test、build 等精确命令，包括必要的执行目录、顺序和单测试、单包等聚焦验证方式；
* 运行时和包管理器要求、环境加载、代码生成、迁移、生成物边界及其他容易遗漏的工具链约束；
* 测试 fixtures、外部服务等前置条件，以及已确认的昂贵、不稳定或特殊测试流程；
* 对有可视化或交互入口的项目，优先调查现有 Compose / Docker 启动方式，其次是源码运行，记录可用命令、必要前置条件和验收入口；无法确认的内容标明未知，初始化时不默认启动程序，也不为此新增容器配置；
* 经仓库证据评估并由用户确认的 Worktree 工作模式和开发模式；
* 现有设计文档和指令来源的必要导航。

## 文档分层

`AGENTS.md` 只保留长期、高频、全局的信息。

尊重现有文档位置和组织方式，包括 `docs/`、`specs/`、`design/`、ADR 或其他已有目录。没有既有约定时，再推荐 `docs/` 存放复杂或低频设计，例如：

* 产品详细设计；
* 架构设计；
* 模块设计；
* API 和数据模型；
* 状态机；
* 外部服务集成；
* 技术决策；
* 迁移方案。

需要时按真实路径在 `AGENTS.md` 中增加简短索引，例如项目已有 `docs/` 时：

```markdown
## 项目文档

- `docs/product.md`：产品与业务流程
- `docs/architecture.md`：系统架构和模块边界
- `docs/scoring.md`：评分逻辑

处理对应领域时按需读取相关文档。
```

初始化不自动迁移、创建或重写详细设计文档，也不为了形式创建空文档。默认只修改根 `AGENTS.md`；额外文档修改需要用户明确要求。

## 不应写入 AGENTS.md

以下通用流程由 `coding` agent 统一负责，不在项目中重复：

* Worktree 开发流程；
* 功能分支管理；
* commit / merge / push 流程；
* 验收和清理流程；
* 通用安全规则；
* 通用开发步骤和汇报格式。

只有当前项目确实需要覆盖默认开发流程时，才在 `AGENTS.md` 写明特例。

## 执行原则

修改前优先检查高价值来源：

* README、贡献指南、根清单、workspace 配置和 lockfile；
* 构建、测试、lint、format、typecheck、codegen 配置及 CI、pre-commit、任务运行器；
* 适用的祖先、根和子目录 `AGENTS.md`，以及现有 `CLAUDE.md`、`.cursor/rules/`、`.cursorrules`、`.github/copilot-instructions.md`；
* 仓库本地 OpenCode 配置及其 `instructions` 引用，只读取非敏感的相关配置，不展开凭证或私密引用；
* 现有文档索引、设计和规格，以及主要目录与包边界。

读取其他工具的规则是为了调查和保留有效项目约定，不代表其自动成为全局指令。保留子目录、文件匹配等适用范围；不要把局部规则提升为全局规则。不要假设生成 `AGENTS.md` 后，运行时仍会自动加载 `CLAUDE.md`，应保留必要约定或明确按需读取来源。

配置和文档仍不足以解释架构时，追踪少量有代表性的入口、调用链和跨包接口，确认系统实际如何连接，不随机遍历叶子文件。关于命令和实际行为，优先采用可执行配置与代码证据；文档冲突要核实，不能据此擅自删除仍有效的人工约定或安全边界。

仓库无法回答关键问题时，只确认当前最关键的一个明确命题；不询问仓库已明确的信息，不根据技术栈模板臆测。

### 项目策略评估与确认

完成仓库调查后，在写入 `AGENTS.md` 前评估后续 Coding 的项目策略：

* 所有需要用户回答的仓库疑问和策略确认都调用 OpenCode `question` 问题框，使用单选、`custom: false`，选项标签严格为“是”和“否”，每次只确认一个有证据的明确命题。无法可靠转换为是非问题时继续最小只读调查；仍无法确认则记录为未知并说明原因，不开放式追问或猜测。
* 先根据仓库类型、目录与工具链、协作方式和本地状态边界评估后续开发是否适合 Worktree，说明判断及依据，再询问用户是否使用 Worktree 工作模式；无论推荐启用或禁用都须确认，未经确认不得写成项目事实。
* Worktree 确认后再评估开发模式。默认推荐 TDD：先建立能失败的测试或问题复现，再做使其通过的最小实现，最后在测试保护下整理代码。只有仓库不适合 TDD，或已有证据表明采用其他开发模式时，才推荐该既有或更合适的模式；不为缺少测试基础设施的配置、纯文档等项目强建测试框架。
* 说明开发模式的判断及依据，再询问用户是否采用该模式，未经确认不得写成项目事实。用户否决后继续最小只读核查，仅在获得新证据时提出一个替代命题；没有可靠替代或再次无法收敛时，将开发模式标为未知并说明原因，不循环询问，也不写入被否决的结论。

### 已有项目的多子 agent 核验

对已有项目建立或更新初始化上下文时，先建立全局目录和模块清单，再主动使用多个只读子 agent 并发调查；不是只读 README，也不是让每个子 agent 重复扫描全仓。

* 默认按架构与主要调用链、工程与验证入口、现有规则与设计文档拆成独立调查任务；大仓库再按包或业务模块拆分，确保主要模块都有明确覆盖者。
* 优先使用可用的 `explore`；需要其他能力时选择实际可用的子 agent，并明确只读授权。传入仓库绝对路径、适用规则、调查范围、待验证问题和返回要求。
* 每个子任务返回已检查的目录和关键文件、带路径的证据、结论、冲突及未覆盖项。主 agent 同时推进未委派的工作，不重复调查。
* 主 agent 汇总全局结构，对跨模块接口、入口到核心流程、文档与代码的一致性进行交叉核验；发现覆盖空白或证据冲突，安排定向补查后再写入 `AGENTS.md`。
* 子 agent 不修改代码、配置或文档，不自行安装依赖、运行有副作用的命令或进行 Git 写操作。初始化核验不等于全仓缺陷审计，也不默认要求执行全部测试或启动服务。
* 极小项目没有可有效拆分的独立范围，或运行时不支持子 agent 时，可以串行调查并说明原因。不得把抽样调查称为逐文件全量验证；最终说明覆盖范围与未验证项。

各子任务完成后，由主 agent 统一编写根 `AGENTS.md`，只纳入已核实且会影响后续工作的事实；没有证据的内容标明未知或省略。

已有 `AGENTS.md` 时以增量维护为主，保留仍然有效的人工约定。

`/init` 属于项目元数据维护任务：

* 直接在当前工作区执行；
* 不创建功能 Worktree；
* 不自动 commit、push 或 merge。

完成后检查：

* 内容是否准确反映当前项目；
* 是否包含未经项目证据支持的推测；
* 是否错误混入通用 Coding 工作流；
* 现有指令中的有效约定是否得到保留，适用范围是否正确；
* 文档和规则引用是否真实存在，是否遵循原有文档布局；
* 多子 agent 的覆盖、冲突和未验证项是否已汇总，关键结论是否有代码或配置证据。
