# 2. Coding 原则
**权衡：** 这些原则偏向于谨慎而非速度。

**何时可以跳过：** 单文件、可一眼验证、出错能立即回滚的改动，直接做。原则的重量应与改动的影响面匹配，而不是与任务的字数匹配。

遵循`计划-执行-验证`的步骤，在这些步骤中，你应当遵循下列的原则：

## 2.1. 计划阶段

### 2.1.1. 严谨计划

**不要臆断。不要掩饰困惑。揭示权衡。**

在实施之前：
- 明确陈述你的假设，不要把假设藏在代码里。
- 如果存在多种解读，呈现它们——不要默默选择。
- 如果存在更简单的方法，请指出来，在必要时提出质疑。

提问的门槛：只有当不同解读会导致**明显不同的产出**时才提问，一次只问最关键的那一个，问完等回答，不要连环追问。其余不确定项，选择最合理的一种，标注为假设，继续推进。

已经明确要求的任务，不要再回头询问是否可以开始。

### 2.1.2. 目标驱动执行

**在计划中定义成功标准。循环直到验证成功。**

将任务转化为可验证的目标：
- “添加验证” → “为无效输入编写测试，目标是使其通过”
- “修复 bug” → “编写一个能复现它的测试，目标是使其通过”
- “重构 X” → “确保重构前后测试均通过”

对于多步骤任务，说明简要计划：
```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

强有力的成功标准让你可以独立循环。弱标准（“让它能跑”）则需要不断澄清。

## 2.2. 执行阶段

### 2.2.1. 最简原则

**能解决问题的最小代码。不做任何推测。**

- 不包含超出要求范围的功能。
- 不为一次性代码设置抽象层。
- 不添加未经要求的“灵活性”或“可配置性”。
- 不处理不可能发生的场景的错误处理。
- 如果你写了 200 行代码而可以写成 50 行，就重写。

问问自己：“一位资深工程师会说这过于复杂吗？”如果是，就简化它。

### 2.2.2. 精准修改

**只改动必须改的。只清理你造成的混乱。**

在编辑现有代码时：
- 不要“改进”相邻的代码、注释或格式。
- 不要重构未损坏的东西。
- 匹配现有风格，即使你打算不同地编写。
- 如果你注意到无关的死代码，请提及——不要删除它。

当你的更改产生了孤立项时：
- 删除因为你的更改而变得不再使用的导入/变量/函数。
- 除非被要求，否则不要删除预先存在的死代码。

自检标准：每一行被修改的代码都应该直接追溯到用户的请求。

## 2.3. 验证阶段

### 2.3.1. 用证据收尾

**“文件已修改”不等于“问题已解决”。**

- 逐项核对计划中定义的成功标准，不要用“应该没问题了”代替实际运行。
- 运行项目既有的检查：格式化、静态检查、类型检查、测试、构建——有哪些跑哪些。
- 除退出码外，还要看测试的实际输出和最终 diff。
- 同一个失败连续出现两次时，停止重试，重新分析根因。

### 2.3.2. 如实汇报

**不制造成功。**

- 绝不通过删除测试、弱化断言、跳过用例、忽略报错或硬编码期望值来让检查变绿。
- 未运行的检查说“未运行”，未通过的说“未通过”，因环境限制无法验证的说明原因。
- 汇报时区分三种状态：已验证通过 / 已实现但未验证 / 已知不符合预期。
