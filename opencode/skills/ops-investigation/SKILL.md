# Ops 深入调查

从用户期望结果倒推调查：要解释原因，就补齐因果证据与关键疑点；要判断影响或比较方案，就取得支持该判断的必要信息；要恢复服务，调查结论交由 Ops 继续完成获准处置和效果验证，不能停在定位原因。目的明确时不例行询问，也不擅自将咨询升级为执行。沿用 [Ops 主代理](../../agents/ops.md) 的目标、连接、授权、凭证保护与查询预算；本技能只提供方法，不授权变更、不接管调度，也不要求调用 Planner 或其他代理。

## 调查方法

1. **明确目的和完成标准。** 固定对象、实际执行环境、预期与实际行为、时间窗口和影响范围，将用户目的转为需要回答的问题、必要步骤和验收依据。区分用户描述与已观察事实；时间线只保留故障、相关变更和恢复等关键节点。普通状态查询直接回答，不为套用流程扩大调查。
2. **沿路径找异常边界。** 从用户症状沿请求、数据或依赖链回溯，比较同一时间的正常与异常样本、配置声明与有效配置、发布版本与实际运行版本。优先定位最早有证据的异常环节，再查其输入和共同依赖；这一环节只是调查起点，不自动等于根因。近期变更是线索，不是定因依据；正常样本须说明与异常样本的可比性。
3. **用假设组织取证。** 保留少量能解释当前现象的候选原因，为每项记下支持、反证、尚缺事实，以及什么观察能将它与其他解释区分开。简单问题无需建表，不凑候选数量。下一次查询必须回答一个可辨别的问题；优先选择低成本、高区分度的证据，不重复无信息增益的扫描。
4. **核对证据，不叠加猜测。** 优先现有监控、有界日志、运行状态、配置与匹配版本资料，记录来源、对象、时间窗口和关键观察。证据冲突时先核对环境、时钟/时区、版本和采样覆盖，再调整假设；不要只选支持自己的结果。日志缺失不等于无异常，查询失败不等于正常，未覆盖的时段不能用当前状态补证。
5. **有条件地验证并收敛。** 需要检验时先说明预期观察、对照、停止条件及可改变的变量；优先已有证据或安全隔离环境，一次只改变可解释的因素。主动复现、负载测试、提高日志级别、安装工具、重启或改配置沿用 Ops 的原授权，不能因用于调查直接执行。不得为证明因果在生产制造破坏性故障。

## 连续推进与收尾

- 仍有能回答原问题、区分假设的获准低风险补证时，由主代理继续完成，不把可立即执行的调查留作最终报告的“下一步”，也不要求用户逐步指挥。证据不足是继续取证的理由，不是自动结束任务的理由。
- 一条路径需要未获准写入或不可用工具时，先检查现有日志、指标、配置和其他安全只读来源能否替代，并继续不依赖该步骤的工作。不得绕过访问限制；跳过的步骤及其影响须如实保留，不能假装证据齐全。关键写入不可替代时按 Ops 原流程请求授权，不把调查目标暗中升级为修复授权。
- 收尾前对照用户目的核查：必要问题是否回答、关键反证是否处理、剩余未知是否影响结论、是否还有可执行且有价值的补证；涉及恢复时核对实际用户症状的验证结果。已解释症状且满足原任务完成标准后停止无关深挖，不无限上溯，也不要求收集所有可能细节。
- 预算耗尽、负载恶化、权限受限或关键证据确实无法取得时，停止受影响的取证；检查其他安全路径是否仍可推进。不能推进时才以明确阻塞或证据边界收尾，说明已完成范围、缺口为何无法补齐及最小待决事项。扩大成本或授权按 Ops 规则处理，不以“完整调查”为由绕过安全边界。必要批准或少量选项用 `question`，长说明放正文，不新增确认步骤。

## 何时可以称为根因

- **已确认原因：** 有可复核的机制链解释异常条件如何造成用户症状；对象和时间对应，关键替代解释及反证已处理。已有证据足够时不强制复现；变更后症状消失只能作为证据之一，不能单独证明因果。
- **较可信假设：** 现有证据支持，但因果链仍有关键缺口或替代解释未排除。明确缺口及能够辨别它的下一步，不写成确定根因，不使用无依据的置信百分比。
- **尚未定位：** 只能确认症状、影响或部分异常边界。直接说明不知道哪一环，不用“环境问题”“偶发问题”等泛称冒充原因。

允许多个条件共同导致故障。按证据区分造成失败的机制、让问题在此时发生的触发因素，以及扩大影响的促成条件；不强求唯一根因，也不机械追问五次。不能从缺少测试或某次操作直接推断组织责任、人员动机或流程缺陷。

紧急缓解可按 Ops 原授权优先进行，不以根因未确定为由阻断合理止损。尽可能保留低成本关键证据，说明缓解可能改变现场；**恢复状态与根因确定程度分别报告**。例如重启恢复并不能证明内存泄漏或死锁。

## 怎么汇报

先给用户需要的判断，再给支撑判断的事实。默认顺序如下，简单问题可合为一段；不强制标题、表格或字数：

1. **结论与确定程度：** 发生了什么、为何发生，或原因尚未定位到哪一步。
2. **关键证据：** 只列决定结论的少量观察，附可复核来源及时间窗口；保留会改变结论的反证或限制。复杂问题展开必要的因果链，不倾倒原始日志、全部假设或逐条命令。
3. **影响与当前状态：** 受影响范围、是否仍在发生、恢复是否已验证；历史故障与当前健康状态分开。
4. **必要下一步：** 只保留真正受阻、需要用户决定或超出本次范围的事项，以及必要的后续观察；说明为何未完成，区分补证、临时缓解和根因修复。已获准且当前可完成的事项应先做，不留给用户催促；已解决且无待办时不凑建议。

调查过程只在解释证据覆盖、重要排除项或用户明确要求时简述，不按“先查了什么、然后又查了什么”组织答案。变更任务的验证、回退、运行任务及 Git/deploy 状态仍按 Ops 交付规则说明；只读调查无需罗列不适用的操作状态。会话内可保留简短证据摘要，不默认创建持久化报告。

### 合成示例（非真实调查结果）

**已确认原因，用户本次只要求查因：** “已确认本次 502 由后端端口配置不一致造成：代理仍连接 8080，新版本只监听 9090。10:02–10:08 的代理错误记录为 8080 连接拒绝，同期后端监听状态和发布配置均为 9090，代理有效配置仍为 8080；故障发生在代理到后端这一段。查因已完成，该入口尚未恢复。修复需统一端口并验证入口请求，本次未授权修改。”用户若要求恢复，Ops 应继续原授权流程，不将这份查因摘要作为恢复任务的最终完成报告。

**已有安全补证完成，仍受历史证据限制：** “重启后请求已恢复，但根因尚未确定。10:00–10:05 的请求指标显示超时，10:06 重启后至 10:15 未再出现。已核对留存日志和监控：没有故障时线程快照，连接池历史指标未采集，现有超时记录无法区分死锁与连接泄漏。历史现场不能由当前健康状态还原；继续查现有数据也无法排除这两种解释。要进一步定因，需要经授权增加定向采集并在复发时取得证据，不建议继续重启试错。”以上缺失与限制均须实际核实，不能套用示例作为早停理由。
